## 1.1 一句话定位

vLLM 的首要目标不是让单个请求跑得最快，而是让**整个 GPU 在单位时间内服务尽可能多的用户**【Source-derived · S1】。

源文档的总结把这条主线说得更完整："vLLM 的核心价值在于**用系统工程的手段，极致地压榨 GPU 的并发服务能力**"——并且给出了它的适用前提：**Transformer 架构的开源模型**、目标是"以尽可能低的成本服务尽可能多的用户或处理尽可能多的数据"，在这个前提下 vLLM "通常是那个最优先、最稳妥的默认选择"【Source-derived · S6】。

这一定位与 vLLM 在 PyPI 上的官方自我描述一致："A high-throughput and memory-efficient inference and serving engine for LLMs"【Research-derived · R1】。两个关键词——**high-throughput**（高吞吐）与 **memory-efficient**（显存高效）——正好对应源文档的两条主线：吞吐优先【S1 / S2c】，以及把显存从"浪费"变成"预算"【S3a / S3b】。

> **请记住这一条主线**，本课程其余六节都是它的展开：
> **vLLM 是拿"单请求延迟"换"整体吞吐"的交换。** 理解 vLLM 的每一个设计取舍，只要问一句"它把延迟让给了谁"就够了。

## 1.2 背景：传统推理框架的两个困境

源文档用"包场餐厅"作类比来讲清楚旧范式的痛点，下面拆成两条**可归因的具体机制**，而不是停留在比喻层面。

### 困境一：组批时机太晚（批级别批处理）

传统推理框架像"固执的领班"：他必须**凑齐一桌客人（一个 Batch）**，等这桌所有人**全部吃完**（所有请求生成完毕），才肯放下一桌人进来【Source-derived · S2a】。

拆开说，这是**静态批处理**的代价：一个批次里的请求共享同一个步数（step），而请求的生成长度由模型自己决定，事先不可知【Source-derived · S2a】。因此只要批次里有一个长请求，整个批次就必须等它跑完才能推进。在这段时间里：

- **GPU 算力闲置**：已经生成完的短请求占着位置却不再产生 token【Source-derived · S2a】；
- **尾延迟被拉长**：新请求排在队尾，等待时间由批次中最慢的请求决定【Source-derived · S2a】。

### 困境二：为每个请求预留大块连续显存（显存碎片）

领班还会为每位客人**预留一张巨大的、固定的桌子**（预分配连续显存），即使这位客人只点了一碗面。这导致餐厅里大部分空间都被浪费——也就是**显存碎片**【Source-derived · S2a】。

根源在于 KV Cache 的两个特点【Source-derived · S2a / Research-derived · R4】：

1. **大小动态可变**：每个 token 都要往 KV Cache 里追加一份 K 和 V，长度事先不可知【Research-derived · R4】；
2. **需要连续空间**：传统实现为每个请求预留一整块连续显存，且**预留量远大于实际用量**（官方博客称之为 "over-reservation"）【Research-derived · R5】。

而预留量大于实际用量的部分，就是纯粹的浪费。这不是"低效"，而是直接**锁死了并发上限**——显存被预留空位占着，就装不下更多请求【Research-derived · R5】。

> **关键因果链**：显存浪费 → 可用并发请求数下降 → GPU 利用率下降 → 吞吐下降。
> 记住这条链，第 [02 节](02-core-concepts.md) 的两个机制正是分别从链尾和链头同时动手。

## 1.3 vLLM 的转向：从"包场"到"拼桌"

源文档给出的解法对应两段拼贴式对比，这是全文最该记住的一张表【Source-derived · S2a / S2b / S2c / S3b】；末行的"优化目标"则是源文档开篇的第一句【Source-derived · S1】：

| 维度 | 传统推理框架（包场领班） | vLLM（拼桌高手） |
|---|---|---|
| 组批时机 | 等整批全部生成完毕才放下一批 | **每个推理步重新组批**，谁吃完谁腾位 |
| 显存分配 | 为每个请求预留固定的大块连续显存 | 按需分配**固定大小的块**，用完立即回收 |
| 空间共享 | 无 | 相同前缀的请求**共享**同一批块（前缀缓存） |
| 优化目标 | 单个请求尽量快 | **整台 GPU 单位时间服务尽可能多的人** |

源文档对结果的表述很克制，值得原样记住：虽然单个客人（请求）的等待时间**不一定最短**，但**整个餐厅的翻台率（吞吐量）实现了飞跃**【Source-derived · S2c】。

这一句话就是 vLLM 的全部设计哲学——它是一个**主动用单请求延迟换取整体吞吐**的系统。

## 1.4 能力边界速览

vLLM 的适用边界由它的吞吐优先目标直接划定【Source-derived · S4a / S4e / S4f / S4g / S4h】。完整的场景分析见 [03 · 核心功能](03-core-functionality.md#capabilities)，工具对比见 [05 · 相关工具](05-related-tools.md)，这里只给一张速览表（下表中【Sxx】均为 `Source-derived` 的简写）：

| 适合 | 不适合 |
|---|---|
| 高并发、多租户的生产服务（聊天机器人、AI 助手、API 平台）【S4a】 | 对冷启动延迟极度敏感、且流量极低需快速扩缩容的场景【S4e】 |
| 大规模离线批量处理（摘要、分类、信息抽取）【S4b】 | 需要 ONNX / TensorRT / PyTorch 等多框架统一编排的流水线【S4f】 |
| 长文本与 RAG（利用前缀缓存复用系统提示词与文档上下文）【S4c】 | 70B+ 模型的多节点 Prefill / Decode 分离式部署【S4g】 |
| 需要 OpenAI API 兼容、零迁移成本接入的场景【S4d】 | **任何训练或微调需求**——vLLM 仅专注于推理【S4h】 |

## 1.5 两个必须先知道的前提

在动手之前，有两条来自官方文档、但源文档没有写明的前提条件：

### 前提一：vLLM 只能在 Linux 上完整运行

官方安装文档写明："vLLM can fully run only on Linux but for development purposes, you can still build it on other systems (for example, macOS) ... The binaries will not be compiled and won't work on non-Linux systems."【Research-derived · R2】

也就是说，在 macOS 上**装得上、import 得进，但跑不了真正的推理**【Research-derived · R2】；Windows 同样不在官方支持平台之列（官方表述为 "can fully run only on Linux"）【Research-derived · R2】。Apple Silicon 用户有一条官方路径：vLLM-Metal，它改用 MLX 作为计算后端，并需要从 `mlx-community` 仓库取模型【Research-derived · R3】。

> **如果你正在 macOS 上读这份课程**：`04-usage.md` 的命令要在 Linux GPU 机器上执行，或者改走 vLLM-Metal / 容器路线。详见 [04 · 使用方法](04-usage.md#platform-check)。

### 前提二：版本会漂移，命令要跟着漂移

本课程编写时，vLLM 的最新版本是 **0.33.0**，发布于 2026-11-02，Python 要求 `>=3.11, <3.15`【Research-derived · R1】。源文档没有标注版本【证据缺口 · UQ1，详见 [07 · 验证记录](07-verification-record.md#unresolved-questions)】，所以你在对照源文档命令时，要以官方文档当前版本为准。

## 1.6 具体例子

### 例子 1 · 拼桌模型如何解释一次调度（Source-derived + Illustrative）

假设服务器上有两个请求：

- 请求 A：输入 200 token，输出 20 token；
- 请求 B：输入 200 token，输出 500 token。

**在批级别批处理下**：两者必须同批次。批次的步数由最长的请求决定，于是**后 480 步（第 21–500 步）**里，A 早已生成完却仍占着批位，GPU 实际只服务 B 一个请求。也就是说，**这 500 步里有 480 步批次是"半空"的**——A 只贡献了 500 步中的 20 步【Illustrative · 计算】。

> **别把这个数字和别处的 "4%" 混为一谈**：这里说的是"A 活跃的步数占比 = 20/500 = 4%"，与 [02 节](02-core-concepts.md)引用的官方博客 "under 4%"（**显存**浪费率）是两回事。

**在连续批处理下**：A 生成完即退出批位。调度器立刻把排队的新请求 C 插入空出的位置，于是从第 21 步起，GPU 同时服务 B 和 C，A 的完成时刻几乎不变【Source-derived · S2b / S3b】。

> 这就是【Source-derived · S2b / S2c】所说的"随吃随走，有空就拼"在时间轴上的含义：
> **单请求延迟（A 的结束时刻）几乎没有变差，整体吞吐却因为批次始终填满而显著上升。**

### 例子 2 · 这个"飞跃"有多大（Research-derived）

vLLM 团队的论文给出了可比数字：在相同延迟水平下，vLLM 将主流 LLM 的吞吐提升了 **2–4 倍**，对比对象是当时的最先进系统 FasterTransformer 与 Orca【Research-derived · R4】。其官方博客在 LLaMA-7B/A10G 与 LLaMA-13B/A100 的 ShareGPT 采样负载上给出的数字更高：相比 HF 高达 **24 倍**、相比 TGI 高达 **3.5 倍**的吞吐【Research-derived · R5】。

> ⚠️ **读这些数字时要注意三点**：
> 1. 这是 **2023 年**的基准，模型、硬件、竞品都换了几轮，不能直接套到你今天的机器上；
> 2. 对比对象里 **TGI 已经进入 maintenance mode**【Research-derived · R13】，这个基线的现实意义已经下降；
> 3. 论文测的是**服务吞吐**，不是**省钱数字**——吞吐提升会摊薄单位请求成本，但换算成具体金额取决于你给硬件定的价。
>
> 这三点与源文档【S4a】"显著降低单位请求的成本"的方向一致，但源文档没有给出量化依据，属于本次研究补齐的部分。

### 例子 3 · 什么时候这笔交换不划算（Illustrative）

> **教学性构造，不主张 vLLM 的任何已验证行为。**

假设你在做一个**交互式代码补全**工具，用户每敲一次回车就等一次结果：

- 你的流量几乎为**空**——每个用户平均每分钟 2 次请求；
- 用户等待的是**这一个请求**，不是"一秒钟内有多少人同时被服务"。

在这个场景下，"用单请求延迟换整体吞吐"这笔交换**两头都不占**：你的并发数根本撑不起批处理，规模效应无从发生；而用户体感到的恰恰就是那个被牺牲掉的延迟。此时源文档提到的 Serverless 路线（如 KServe）才更匹配【Source-derived · S4e】——见 [05 · 相关工具](05-related-tools.md#selection-chain)。

## 本节小结

- vLLM 的目标函数是**整体吞吐**，不是单请求延迟【S1】；源文档的总结把它定性为"用系统工程的手段，极致地压榨 GPU 的并发服务能力"【S6】。
- 传统范式的两个浪费源头：**组批太晚**（等整批结束）与**显存预留过大**（碎片 + 过度预留）【S2a】。
- vLLM 的两个机制（连续批处理、分页注意力）分别在调度层和内存层解决了这两个源头——见 [02 · 核心概念](02-core-concepts.md)。
- 边界由吞吐优先目标划定：**推理专用**，不是训练框架，也不是多框架编排器【S4f / S4h】。
- 动手前先确认：**Linux + GPU**，并对齐当前版本【R1 / R2】。
